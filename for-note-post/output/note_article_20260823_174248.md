# SWE-bench Science：科学コードのrepo-level修正で最上位モデルでもpass@1<50%——4大失敗機構を解明した新ベンチマーク

## この記事で得られること

- **科学SWEにおけるAIエージェントの実力ラインが一目でわかる**：Claude Code（Opus-5 max）を含めた最上位モデルでもpass@1が50%を割るという結果から、「科学コードのリポジトリレベル修正」がまだ自律解決の域に達していないことを定量的に把握できる。チーム内でAI辅助デバッグの期待値設定やヒューマン・イン・ザ・ループ設計の必要性を議論する際の根拠資料としてそのまま使える。
- **失敗原因の4分類フレームワークが手に入る**：(1) 科学知識・ドメイン抽象の欠如、(2) 誤った探索や表面的なパッチ適用、(3) 修正カバレッジの不完全さ・システム統合失敗、(4) テストケースへの過剰適合——という4大失敗機構の分類法を獲得できる。自社エージェントのログ解析や評価パイプライン設計に直接適用可能。
- **3タスクパラダイムによる評価設計のテンプレートが得られる**：Issue駆動型／Expert探求型／Engineering統合型の3軸でエージェント能力を切り分ける設計思想がわかる。モデルアップグレード時のリグレッションテストや、科学産業（製薬・航空宇宙・エネルギー）向けデプロイ前の内部評価スイート構築にそのまま転用できる。
- **科学的ガイダンスの与え方がエージェント性能にどう影響するかの実証データが読める**：アブレーション実験から、「正確かつスコープが絞られた」ドメイン知識は検索空間を絞ってトークン消費を減らす一方、曖昧・不正確なヒントはアンカリング効果を誘発し逆効果になることが示される。RAGパイプラインやツール拡張型エージェントのコンテキスト設計に直結する知見。
- **既存ベンチマークとの差分と補完関係が明確になる**：SWE-bench / Multi-SWE-benchがWeb・システム・汎用Python/JSリポジトリに偏っているのに対し、本ベンチマークは20の科学ドメイン（物理・生物・化学・材料・天文学など）98リポジトリ・119タスクをカバー。科学ソフトウェア領域のギャップをどう埋めるかの全体像を把握できる。
- **200kLOC規模のシミュレーションコードベースを持つチーム向けの具体的な活用シナリオ**：保存則・熱力学的整合性など汎用ユニットテストでは検出できないドメイン不変条件を、AI辅助デバッグパイプラインが捕捉できるかをストレステストする方法論を得られる。

# SWE-bench Science: 技術的な要約

## SWE-bench Scienceとは何ですか？

SWE-bench Scienceは、科学的ソフトウェアエンジニアリング（SWE）タスクを実行する際の自律的なコーディングエージェントの能力と障害モードを評価することを目的としたリポジトリレベルのベンチマークです。
一般的なコーディングベンチマーク（例えば、元のSWE-bench）とは異なり、このベンチマークは関数や単一ファイルレベルで動作するのではなく、科学的なコードが測定または解析の儀器の一部である全体のリポジトリの問題をターゲットにしています。つまり、バグが科学的主張の証拠基盤を破壊する可能性があるため、より高度な評価が必要です。
ベンチマークは98つの実際のGitHubリポジトリから119つのタスクを収集し、物理学、生物学、化学、材料科学、天文学など20の異なる科学的領域をカバーしています。これにより、エージェントの評価はこれまでに最も分野多様なものとなっています。
このベンチマークはHugging Face Daily Papers（arXiv識別子2608.19799）を介して発表され、コーディングエージェントが科学的コードで失敗する*理由*を理解するための診断テストベッドとして位置付けられています。つまり、エージェントが成功したかどうかだけでなく、エージェントが失敗する*理由*を理解することが重要です。

## 仕組み – タスク構造と評価プロトコル

### 3つのタスクパラダイム

- **Issue-driven**: エージェントはGitHubスタイルの問題記述を受け取り、リポジトリ内の基礎的なデフィクトを特定し、修正する必要があります。
- **Expert-exploratory**: エージェントは曖昧または高レベルの研究質問を受け取り、コードベースをナビゲートし、仮説を形成し、正確なバグレポートなしで修正を実装する必要があります。
- **Engineering-integration**: エージェントはリポジトリ全体でコンポーネントを修正または統合する必要があります。これは単一の機能の正確さではなく、システム全体の連続性をテストします。

### 評価指標

主に報告される指標は**pass@1（単一試行での正確な修正率）**です。エージェントが1回で正確で完全な修正を行うことが求められています。

### ペアアブレーション研究

著者は、明確な科学的なガイダンス（例えば、ドメイン固有のヒント、期待される物理的/化学的行動）を削除しながら、完全なリポジトリのコンテキストと実行可能なエンジニアリング環境（ユニットテスト、リンティング、型チェック）を保持した制御比較を実行しています。これにより、科学的な知識のマージナルな貢献を生のコーディング能力から分離できます。

### 失敗メカニズム分類

すべての失敗は手動で4つの繰り返しするメカニズムの1つに分類されます：
1. 科学的知識やドメイン抽象の欠如（エージェントはコードにエンコードされた物理学/生物学/化学を理解できない）。
2. 失敗した探索または表面的な修復（エージェントは症状をパッチすることなく根本原因を特定しない、または間違ったモジュールを検索する）。
3. 部分的な修復カバレッジやシステム統合の失敗（エージェントが1つの機能を修正するが、下流の依存関係を破るか、結合されたコンポーネントを無視する）。
4. 観測されたテストケースを超えて科学的知識を一般化できない（特定のテストハーネスに過剰適合する代わりに、正しいドメインの不変性をエンコードできない）。

## 主な定量的な発見

最もパフォーマンスの高い評価されたエージェント**Claude Code with Opus-5 (max)**は**pass@1が50%以下**を達成しています。これは、フロンティア規模のモデルがリポジトリレベルの科学的ソフトウェアエンジニアリングタスクの半分以上で失敗するということを示しています。
アブレーションでは、科学的なガイダンスを削除した結果が混合しました：
- ガイダンスが*適切に根拠付けられている*（正確で適切な範囲）場合、検索空間が制限され、平均的な通過率が向上し、トークン消費量が修理ごとに減少します。
- ガイダンスが*不正確に合わせられている*（曖昧、わずかに不正確、または範囲が不適切）場合、アンカー効果が引き起こされます。エージェントは誤ったヒントにロックされ、トークンを無駄に使い、修理の正確性はガイドなしのベースラインと同様に向上しません。
どの単一のエージェントも全3つのパラダイムで優位ではありません。パラダイム間のパフォーマンスのギャップ（特にExpert-exploratoryセット）は、エージェント間のギャップよりも広く、タスクのフレーミングとドメインの理解が生のコード生成能力よりも制限的な要因であることを示しています。

## 開発者、研究者、および科学的ソフトウェアエコシステムにとってなぜ重要ですか？

### 科学的な結論の信頼性

遺伝学、気象モデリング、粒子物理学、計算的化学など、分析コードに静かなバグが存在すると、発表された結果が無効になる可能性があります。エージェントがそのようなコードを*修正*できるかどうかを明示的に測定するベンチマーク（ゼロから書くだけではなく）は、AIが実験室や野外ソフトウェアで使用されるための重要な要件です。
### エージェント製品開発

4つのメカニズム分類は、LLMベースのエージェント開発者（Devin、SWE-agent、IDE統合コピロットを構築するチームなど）に具体的な失敗カテゴリを提供します。これにより、トレーニングデータ、ツール使用のスケルトン、評価パイプラインに焦点を当てることが可能になります。
### コンテキストウィンドウとツール設計

アブレーションからのトークン効率の結果は、*正確で適切な範囲*の科学的なコンテキスト（単に長いドメインの概要だけではなく）が、検索強化やツール強化エージェントをガイドするため、より効果的であることを示しています。これにより、生産エージェントパイプラインでのコンテキストの構築方法が指示されます。
### ベンチマークのギャップの埋め合わせ

以前のベンチマーク（SWE-bench、SWE-bench-Live、Multi-SWE-bench）は、ウェブ、システム、汎用的なPython/JSリポジトリに傾向にあります。SWE-bench Scienceは20の科学的領域とリポジトリレベルの統合タスクを導入し、エージェント評価のランドスケープで以前に未表露のニッチを埋め合わせています。
### 再現性とオープンな科学

ベンチマークは公開のGitHubリポジトリから構築されているため、どのラボでも評価を再現し、新しいドメインタスクを貢献するか、失敗の注釈を監査することができます。これにより、科学的ソフトウェアエンジニアリングの進行状況を透明に追跡することが可能になります。

## 具体的なユースケースと実践的な取り組み

### 生物計算チーム

生物計算チームは、200 kLOCのシミュレーションコードベースを維持しています。SWE-bench Scienceのタスクフォーマットを使用して、内部のAI支援デバッグパイプラインが一般的なユニットテストが見落とすドメイン固有の不変性（例えば、保存法、热力学的一貫性）をキャッチするかどうかを試験的に検証することができます。
### LLMエージェントベンダー

LLMエージェントベンダーは、Issue-driven / Expert-exploratory / Engineering-integrationの3つのパラダイムの分割を内部の評価スイートとして採用することができます。これにより、モデルのアップグレードをリリース前に科学産業のクライアント（薬品、航空宇宙、エネルギー）にデプロイする前に、リグレッションテストを行うことができます。
### 取得強化エージェントの構築者

取得強化エージェントの構築者は、アブレーションプロトコルをテンプレートとして使用することができます。ドメイン知識の取得ステップと取得なしのコントロールを組み合わせて、科学的なコンテキストの*総合的*貢献量と純粋なコードコンテキストの論理を量定することができます。
### 50%未満のpass@1の上限

この上限は現実的な基準を提供します。チームは単一のショットでの自律的な修正を期待すべきではなく、特にEngineering-integrationとExpert-exploratoryパラダイムで失敗率が最も高い場合、エージェント出力を人間介入のレビューゲートで設計すべきです。

### 現場での具体的インパクトと適用場面

SWE-bench Scienceが提示するデータは、単なる学術的評価指標にとどまらず、現行のAIエージェント導入戦略を根本から再設計せざるを得ない実務的シグナルである。特にpass@1が50%を下回っているという事実は、科学ソフトウェアの保守・修復という最もリスクの高い工程において、現行のフロンティアモデルですら「一度で正しく直す」確率が半数未満であることを定量で示しており、これを前提としていない本番運用設計は構造的に脆弱である。具体的には、ゲノム解析パイプライン、気候シミュレーション、計算化学、素粒子物理の検出器解析といった、コード内の1行の誤りが論文の結論そのものを無効化するドメインにおいて、エージェントの出力をそのまま本番環境に反映する「autonomous fix」モデルは現実的ではない。代わりに、エージェントを「候補修復案の生成器」として位置づけ、領域専門家によるレビューゲートを工程に組み込むhuman-in-the-loop設計が、現時点での唯一の安全な運用パターンとなる。

この設計判断を裏付けるのが、四分類の失敗機構分類法である。現場のSREチームやQAエンジニアリング部門がエージェントの出力を監査する際、単に「通った／通らなかった」の二値ではなく、(1)科学的知識の欠如、(2)表面的なパッチ適用、(3)下流依存関係の破損、(4)テストケースへの過学習、という四つの軸で失敗を分類・蓄積することで、モデルアップグレード後の回帰テスト設計やプロンプト・スクラフィングの改善方向が構造的に定まる。例えば、計算生物学のシミュレーションコードベース（20万行規模）を保守するチームが、質量保存則や熱力学整合性といったドメインインバリアントを検証する際、汎用的なユニットテストでは捉えきれない不整合を、エージェントが「表面的なパッチ」で隠蔽するリスクは、この分類法の(2)と(4)に明確にマッピングされる。したがって、本番環境に配置するエージェントの監査ログには、単なるdiffではなく、どの失敗機構に該当するかのタグ付けを必須項目として設計すべきである。

アブレーション実験の知見が、プロダクション環境におけるコンテキストアセンブリ設計に直接転用可能である点も、現場レベルでのインパクトとして重要である。科学的ガイダンスが「適切にスコープされた」場合、探索空間が収束しトークン消費が減少して修復成功率が向上する一方、「曖昧でスコープが外れた」ガイダンスがアンカリング効果を誘発し、むしろベースラインを下回るという結果は、RAGパイプラインやツール拡張型エージェントの設計指針として即座に適用できる。つまり、ドメイン知識の「量」ではなく「精度とスコープの妥当性」がエージェントの修復品質を左右するということである。製薬、宇宙航空、エネルギー業界向けにLLMエージェントを納入するベンダーは、このアブレーションプロトコルを内部評価スイートに組み込み、ドメイン知識検索ステップの有無・精度をパラメータとしてスキャンする回帰テストを、モデルアップグレードのたびに実行する運用体制を構築すべきである。

三パラダイムの分割（Issue駆動型／専門家探索型／エンジニアリング統合型）は、現場のテスト戦略設計において、エージェントの「何を問うか」が「どのモデルを使うか」よりも性能変動に大きく寄与するという事実は、評価コストの配分を再考させる。特にExpert-exploratoryセットでモデル間差が最も小さく、タスクフレイミングの差が支配的であるという結果は、本番運用においてエージェントに与える指示の粒度・抽象度・ドメイン前提の明示度が、モデル選定そのものよりも重要な設計変数であることを示唆する。したがって、科学ソフトウェアの保守チームは、エージェントへの指示テンプレートを「バグ報告書形式」「研究質問形式」「統合要件書形式」の三つに標準化し、それぞれに対する期待品質とレビュー深度を事前に定義する運用設計が、モデルの世代交代に依存しない安定した品質保証枠組みとなる。

最後に、このベンチマークが公開GitHubリポジトリから構築されており、20の科学ドメインにまたがる119タスクが再現可能であるという特性は、オープンサイエンスの文脈において、エージェントの科学ソフトウェア修復能力に関する進捗を追跡可能な共通尺度を提供する。各研究所が自ドメインのタスクを追加贡献し、失敗アノテーションを相互監査する仕組みが機能すれば、エージェントの科学SWE能力は「ベンダーが主張する数値」ではなく、コミュニティで検証された透明な指標として追跡可能になる。これは、科学ソフトウェアの信頼性保証が属人的・暗黙的な知見から、再現可能な工程指標に基づくガバナンスへと移行するための、現場で最も具体的かつ即座に着手可能なインフラ整備である。
