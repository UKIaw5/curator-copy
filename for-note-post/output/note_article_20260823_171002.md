# SWE-bench Science：科学SWEタスクでFrontier Agentのpass@1は50%未満

## この記事で得られること

- **科学コードにおけるAgent失敗の構造的理解**：単なる正解率の数字ではなく、なぜ失敗するのかを4つのメカニズム（科学的知識の欠如・表面的な修正・系统集成の失敗・テスト過学習）に分解した診断フレームワークを把握できる。
- **3つのタスクパラダイムによる評価設計の知見**：Issue駆動型／専門家探索型／エンジニアリング統合型のそれぞれがAgentの異なる能力軸を測定しており、自社パイプラインの弱点特定にそのまま転用可能な設計思想が得られる。
- **科学的ガイダンスの効果と副作用**：適切な領域知識の提供は探索空間を絞りToken消費を削減する一方、不正確・曖昧なヒントはアンカリング効果を引き起こし、無ヒントベースラインすら下回る——この二面性がRAG型Agentのコンテキスト設計に直接的に反映される。
- **Agent開発チームへの具体的ターゲット**：Devin・SWE-agent・IDE統合Copilot等の開発チームが、学習データ・ツール活用スキャフォールド・評価パイプラインのどこに手を打てばよいのか、4分類の失敗カテゴリが明確な改善指針となる。
- **科学ソフトウェアの信頼性リスクの定量化**：ゲノミクス・気候モデリング・粒子物理・計算化学等领域で、1つのサイレントバグが公開結果を無効化しうる——Agentがコードを「書く」ことではなく「修正できる」かを測るベンチマークの重要性が理解できる。
- **実務設計の現実的な前提**：pass@1が50%未満という数値は、複雑な科学SWEで単発の自律修正を期待すべきではないことを示しており、Engineering-integrationとExpert-exploratory領域では必ずヒューマンインザループのレビューゲートを設計すべきという判断根拠が得られる。
- **再現可能なオープン評価基盤の活用方法**：公開GitHubリポジトリから構築されており、自社ドメインのタスク追加・失敗アノテーションの監査・他ベンチマークとの比較が自由に実施できる。

# SWE-bench Science: 技術的な要約

## WHAT IT IS

SWE-bench Scienceは、科学的ソフトウェアエンジニアリング（SWE）タスクを実行する際の自律コードエージェントの能力と故障モードを評価するためのリポジトリレベルのベンチマークです。
一般的なコードベンチマーク（例えば、オリジナルのSWE-bench）とは異なり、このベンチマークは関数レベルや単一ファイルレベルではなく、科学コードが測定または分析ツール自体の一部として機能する全体的なリポジトリ問題をターゲットとしています。これは、バグが科学的主張の証拠ベースを破壊する可能性があるためです。
ベンチマークには、98つの実際のGitHubリポジトリから抽出された119つのタスクが含まれており、物理、生物学、化学、材料科学、天文学など20の異なる科学領域がカバーされています。これにより、これが現存する最も多様なドメインを含むエージェント評価の一つとなります。
このベンチマークはHugging Face Daily Papers（arXiv識別子2608.19799）で発表され、コードエージェントが科学的コードで失敗する*理由*を理解するための診断テストベッドとして位置付けられています。

## HOW IT WORKS – タスク構造と評価プロトコル

**三つのタスクパラダイム**が使用され、異なるエージェントの能力を試します：
1. *Issue-driven*：エージェントはGitHubスタイルの問題記述を受け取り、リポジトリ内の根本的な問題を見つけ、修正する必要があります。
2. *Expert-exploratory*：エージェントは不明確なまたは高レベルの研究質問を受け取り、コードベースをナビゲートし、仮説を立て、精密なバグレポートなしで修正を実装する必要があります。
3. *Engineering-integration*：エージェントはリポジトリ全体のコンポーネントを修正または統合する必要があります。これは個々の機能の正確性をテストするのではなく、システムレベルの連続性をテストします。
**評価メトリクス**：主に報告されるメトリクスはpass@1（単一試行での正確な修復率）であり、エージェントが最初の試行で完全に正確な修復を生み出すことを強調しています。
**ペアドアブレーション研究**：著者は、明確な科学的ガイダンス（ドメイン固有のヒント、期待される物理/化学的行動など）を削除しながら、完全なリポジトリのコンテキストと実行可能なエンジニアリング環境（ユニットテスト、リンティング、タイプチェック）を保持した制御比較を実行しています。これにより、科学的な知識の边际的な貢献を生のコーディング能力から分離できます。
**故障メカニズム分類**：すべての失敗は手動で4つの繰り返し現象のいずれかに分類されます：
1. 科学的知識またはドメイン抽象の欠如（エージェントがコードにエンコードされた物理学/生物学/化学を理解していない）。
2. 不正確な探索または表面的な修復（エージェントが症状をパッチし、根本的な原因を特定しない、または間違ったモジュールを検索する）。
3. 不完全な修復範囲やシステム統合の失敗（エージェントが1つの機能を修正するが、下流依存関係を壊したり、関連するコンポーネントを無視する）。
4. テストケースに限られた観測値を超えて科学的知識を一般化できない（特定のテストハーネスに適合するのではなく、正しいドメイン不変をエンコードしない）。

## KEY QUANTITATIVE FINDINGS

評価された最良のエージェント—**Claude Code with Opus-5 (max)**—が達成するpass@1は**50%未満**で、フロンティア規模のモデルもリポジトリレベルの科学的ソフトウェアエンジニアリングタスクの半数以上で失敗すると示しています。
アブレーションで科学的ガイダンスが削除された場合、結果は以下のようになります：
1. ガイダンスが*well-grounded*（正確で適切な範囲）である場合、検索空間が制限され、平均的なパスレートが向上し、修復ごとのトークン消費が削減されます。
2. ガイダンスが*poorly aligned*（不明確、多少誤り、範囲外）である場合、アンカー効果が引き起こされます：エージェントは誤ったヒントに锁定し、トークンを無駄に使い、no-guidanceベースラインよりも正確な修復に成功することはありません。
どのエージェントも3つのパラダイムのうちいずれかで優れていません；パラダイム間のパフォーマンスのギャップ（特にExpert-exploratoryセット）は、エージェント間のギャップよりも大きく、タスクのフレーミングとドメインの論理が生のコード生成能力よりも制限的な要因であることを示しています。

## WHY IT MATTERS TO DEVELOPERS, RESEARCHERS, AND THE SCIENTIFIC SOFTWARE ECOSYSTEM

**科学的な結論の信頼性**：ゲノミクス、気象モデル、粒子物理学、計算化学などの領域では、分析コードのサイレントバグは発表された結果を無効にする可能性があります。エージェントが*修正*できるかどうかを明示的に測定するベンチマーク—単に新規に書くだけではなく—is AIが実験室や野外ソフトウェアで使用されるための重要な指標です。
**エージェント製品開発**：四つの故障メカニズム分類が、LLMベースのエージェント開発者（Devin、SWE-agent、IDE統合コピルートを構築しているチームなど）に具体的な失敗カテゴリを提供します。トレーニングデータ、ツール使用スキャフォールディング、および評価パイプラインを対象にします。
**コンテキストウィンドウとツール設計**：アブレーションからのトークン効率の見解は、*正確で適切な範囲*の科学的コンテキスト（単に長いドメインの概要を提供するだけでなく）が、検索強化またはツール強化エージェントをガイドするのに効果的であることを示しています。これにより、生産エージェントパイプラインでコンテキストが組み立てられる方法が明確になります。
**ベンチマークのギャップの埋め合わせ**：以前のベンチマーク（SWE-bench、SWE-bench-Live、Multi-SWE-bench）はウェブ、システム、一般的なPython/JSリポジトリに傾向があります。SWE-bench Scienceは、20の科学的領域とリポジトリレベル統合タスクを導入し、エージェント評価のランドスケープにおける以前未対応のニッチを埋めています。
**再現性とオープン科学**：ベンチマークが公開のGitHubリポジトリから構築されているため、任意のラボが評価を再現し、新しいドメインタスクを追加したり、失敗の注釈を監査したりすることができ、科学的ソフトウェアエンジニアリングにおける透明な進行状況を追跡することができます。

## CONCRETE USE CASES AND PRACTICAL TAKEAWAYS

**Computational Biologyチームが200 kLOCシミュレーションコードベースを維持している場合**、SWE-bench Scienceのタスクフォーマットを使用して、内部のAIアシスタントデバッグパイプラインが一般的なユニットテストが見逃すドメイン固有の不変量（例えば、保存則、熱力学の一貫性）をキャッチするかどうかをストレステストすることができます。
**LLMエージェントベンダーが三つのパラダイム分割（Issue-driven / Expert-exploratory / Engineering-integration）を使用すると**、内部の評価スイートとしてモデルのアップグレードをリグレッションテストし、科学業界のクライアント（薬品、航空宇宙、エネルギー）に展開する前に使用することができます。
**検索強化エージェントを構築している研究者**は、アブレーションプロトコルを使用することができます：ドメイン知識の検索ステップを、検索なしのコントロールと組み合わせて、科学的コンテキストと純粋なコードコンテキストの論理の*総貢献*を量度します。
**50%未満のpass@1の上限**は現実的な基準を提供します：チームは単一の試行の自律的修正を期待すべきではないので、特にEngineering-integrationやExpert-exploratoryパラダイムで失敗率が高い場面で、エージェント出力を人間インザループレビューのゲートを設計すべきです。

### 現場での具体的インパクトと適用場面

SWE-bench Scienceが提示するデータは、単なる学術的ベンチマークの報告にとどまらず、科学計算ソフトウェアを運用する現場のアーキテクチャ設計やAIエージェント導入戦略に直接的な設計制約として機能する。特に注目すべきは、最上位エージェント（Claude Code / Opus-5 max）でさえpass@1が50%を割り込むという事実である。これは、20万行規模のシミュレーションコードベースを維持する計算生物学チームや、粒子物理の解析パイプラインを運用する実験施設において、「AIが単発でバグを修正してくれる」という前提を設計方針に据えることは、現在のモデル能力に対して非現実的であるという明確なシグナルである。具体的には、以下のような現場レベルの設計判断が要請される。

- 保守パイプラインへの組み込み方：SWE-bench Scienceの三パラダイム（Issue駆動型／専門家探索型／エンジニアリング統合型）は、生産環境におけるAI支援デバッグの実装レイヤーを設計する際の分類軸として直接転用可能である。Issue駆動型に相当する「チケットから修正」のシナリオでは、エージェントの出力をCI/CDの単体テストゲートに直結させればよい。一方、専門家探索型（曖昧な研究課題から根本原因を特定する）とエンジニアリング統合型（リポジトリ横断の結合修正）では、pass@1の低下が最も顕著であり、ここで人間のレビューゲートを省略すると、下流の依存コンポーネントが破損したまま本番環境に流入するリスクが実在する。したがって、これらのパラダイムに該当するタスクには、エージェント出力の差分をドメイン専門家（物理学者、化学者、生物情報学者）が確認する二重審査プロセスをアーキテクチャに組み込むべきである。

- 失敗メカニズムの四分類が示す運用設計：（1）科学的知識の欠如、（2）表層修復・誤った探索、（3）修復の不完全さ・システム統合失敗、（4）テストケースへの過学習——この四分類は、生産環境でのAIエージェント監査ログのタグ体系としてそのまま採用できる。例えば、製薬企業の計算化学チームが内部エージェントの失敗事例を蓄積する際、この分類に基づいて「どの種の失敗が最も頻出するか」を四半期ごとに定量把握することで、トレーニングデータのパイプラインやツールユースのスケフォールドの改善優先順位を客観的に決定できる。特に（3）の「一箇所を直して下流を壊す」パターンは、モジュール間の暗黙のドメイン不変条件（熱力学的一貫性、質量保存則、量子数の保存）が単体テストでは捕捉されないケースに該当し、統合テストスイートの設計見直しを迫られる。

- 文脈アセンブリの設計原則：アブレーション実験が示す「適切にスコープされた科学的ガイダンスは検索空間を絞りtoken消費を削減する一方、不正確・曖昧なガイダンスはアンカリング効果を誘発し、むしろベースラインを下回る」という結果は、RAG（検索拡張生成）やツール拡張エージェントの文脈ウィンドウ設計に直接的な設計制約を課す。現場では、ドメイン知識を「長い解説文書」ではなく、修正対象モジュールに限定された不変条件の宣言（例：「この積分ループではエントロピーが単調増加する」）として構造化し、エージェントのプロンプトに注入する方が、汎用的な分野概要を数千tokenで与えるより効果的である。この知見は、アエロスペースやエネルギー分野におけるAI支援コードレビューツールを実装するベンダーにとって、プロンプト設計のROIを最大化する実務指針となる。

- ベンチマークを「インフラ」として運用する観点：119タスク・98リポジトリ・20科学分野という規模は、小規模な研究ラボが自前の評価スイートを構築する際の最小構成として十分機能する。公開GitHubリポジトリを基盤としているため、自らの研究分野（例：天体物理のN体シミュレーション、材料科学のDFTコード）に固有のタスクを追加し、内部モデルアップグレードの回帰テストとして四半期ごとに実行する運用が成立する。これにより、「モデルをv7に切り替えたところ、Issue駆動型タスクのpass@1は12%向上したが、エンジニアリング統合型では3%低下した」という粒度の意思決定が可能となり、科学産業クライアント（製薬、宇宙、エネルギー）へのデプロイ判断が定量的に裏付けられる。

- 最終的な設計結論：SWE-bench Scienceのデータが示す本質的なメッセージは、「科学ソフトウェアにおけるバグは、コードの正誤問題ではなく、科学的主張の証拠基盤の破綻である」という点にある。汎用コーディングベンチマークでは「関数が正しい出力を返すか」が判定基準であるのに対し、本ベンチマークでは「修正後のコードが物理法則・化学的制約・生物学的不変条件を満たすか」が判定基準となる。この認識の差が、現場でのAIエージェント導入における最大の設計分岐点であり、pass@1が50%以下であるという数値は、能力の欠如を示すだけでなく、科学ソフトウェアの保守が本質的に「コード理解」と「ドメイン理解」の両立を要求する複合問題であるという構造的難易度を定量化している。したがって、生産環境でのAI支援は、単発の自律修正ではなく、エージェントの提案を人間が科学的妥当性の観点から検証する共創プロセスとして設計されるべきであり、その検証プロセスの品質が、最終的に科学結論の信頼性を保証するボトルネックとなる。
